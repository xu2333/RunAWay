# Can a project card retain a distinction that changes implementation?

This is a repair test on the [previously scored design task](../../docs/results/real-demo-learning-card-v1.md). The prior card retained an owner's cross-game goal but omitted an earlier assistant's proposed distinction between menu actions and continuous controls. The candidate adds a general instruction to retain an implementation boundary, its source and its status as a proposal. It names neither the domain nor the lost detail. The schema still requires user support for each decision claim. The existing product default is the concurrent baseline.

## Comparison

Use the [original builders and validator](../real-recording-card-v1/protocol.py) and the [candidate instruction and order](comparison.py). Each encoder sees only the same 27 prior messages. Each method generates two independent whole cards of at most 768 Unicode characters including the header. Each card is used in two independent deliveries. Four additional deliveries use the same seven current messages with either no memory or all prior text, twice each. The reader sees only its assigned context. Generated profiles, the previous card, scores, source labels and rubric are never additional reader inputs. Sixteen attempts maximum. A failed call, invalid artifact or unavailable usage closes the run with missing slots retained. No retries or repairs.

## Frozen assessment

Shuffle and conceal arm and generation labels before assessing all twelve plans. Save judgments and supporting excerpts before inspecting cards or revealing assignments. The grader knows the case. The study has one owner, one retrospective task and two generations per method.

- **Usable plan.** Explain how demonstrations become an executable procedure and how to check successful execution.
- **Transfer.** Retain the original criterion. Identify a concrete part of the learning or execution pipeline that works in a different game, and how another game's task or interface can fit. Robustness to a changed screen within one game leaves transfer unclear.
- **Control boundary.** Make a concrete distinction between discrete interface actions and continuous movement, camera or combat, with an operational consequence such as different learned controllers, duration-aware trajectories or simultaneous inputs. Listing action names, logging taps, or generic gesture support alone is insufficient. Multi-touch is recorded separately. An assertion that the owner mandated a suggested controller or that it already works is an attribution error.
- **Joint retention.** Each plan must pass quality, transfer and control boundary together, without that attribution error. Report the individual criteria and joint result for all plans. Each card requires both deliveries to pass. A method requires both generated cards to pass. Report the two full-text and two current-only deliveries too, including unclear, contradicted and missing judgments. If both extraction methods succeed, there is no observed repair advantage.
- **Displacement.** After locking the delivery scores, trace each item through prior source, extracted claims or qualifications, portable text and delivery. Compare against both fresh baseline cards and the previously archived card. Predeclared collateral items are phone-first with tablet acceptable, repeated demonstration followed by takeover with readiness uncertain, starting with one game allowed, making progress while a device is unavailable, and a guided interface with one or two buttons per page. Also audit uncertainty about local versus assisted execution and distinguish assistant suggestions from owner commitments. Record partial losses (including numeric or scope qualifiers), gains, omissions and contradictions per card, with any additional lost content listed separately. A plan need not volunteer unrelated device or UI details; their absence from that answer alone cannot establish displacement. Missing outputs stay in every planned denominator.

Compare card lengths and distinguish a loss in extraction from information present in a card but unused by the reader. Displacement here is an observed content difference; stochastic generation and unused budget limit causal claims. Success on this targeted repair would still need an unseen task before changing the default. The private source, exact inputs, outputs and rating excerpts stay local.

The [measured result](../../docs/results/real-control-boundary-v1.md) reports all four cards, six returned plans and the timeout.
