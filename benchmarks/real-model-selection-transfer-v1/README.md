# Does the fixed-card reader transfer to a real model-selection task?

A benchmark designer asked which models to test if a shared GPU became available. The immediate exchange described machine rules and the apparent availability of one model family. Earlier, the owner had asked to calibrate with less prominent models, save prominent models for final evaluation, and focus that final evaluation on leaders of a named index. The owner also accepted a procedure that separated model roles and froze the benchmark before inspecting final results. The immediate exchange contains neither that separation nor the intended final population. The choice of a model-selection question is retrospective. Its domain and scoring endpoint differ from the previously studied demonstration-learning and recording tasks. The same owner supplied all three.

The input ends at the actual question. The task asks for a plan, so a reader can answer without using the machine, inspecting its inventory, downloading models or looking up today's rankings. A family mentioned by the owner is a lead, not confirmation of a checkpoint, independence or eligibility. Generic benchmark practice could itself elicit separation. The history control measures this.

## Frozen comparison

Use the [composition](protocol.py) of the previously evaluated [switch encoder](../real-control-switch-v1/encoder.py), original portable-card validator and [revised reader](../real-fixed-card-reader-v1/reader.py). No case-specific instruction is added to extraction or delivery. Generate two independent whole cards of at most 768 Unicode characters, using only the available earlier text. Each resulting string, including header and final newline, is fixed across both readers and both repetitions. Both readers receive the same actual current exchange. Add two deliveries with that exchange alone and two with the full eligible earlier text using the original task reader. Fourteen serial attempts at most: two extractions and twelve deliveries. Only the card readers see the generated card. The revised reader is tested in the presence of memory; there is no revised-reader/no-card arm. This cannot separate a general instruction effect from an interaction with memory.

Inputs comprise chronological user and assistant text with local links, connection identifiers and operational access details removed. The original answer to this task, subsequent corrections, raw tool outputs, credentials, scores and prior cards stay out of all requests. Request gpt-6.1-sol via Codex, up to 180 seconds per attempt, no token or monetary cap. An invalid artifact, failure or unknown usage closes the remaining scope. No retries, card editing, recovery or replenishment. Every planned slot stays in the denominator.

## Evidence before opening condition labels

Assess each shuffled plan against these same predeclared questions with excerpts. Accept equivalent plans and conditional candidates. Do not require one particular model name.

- **Task quality.** Give at least one identifiable candidate model or checkpoint family with a concrete selection condition, its role or purpose, and an actionable first run or ordering. Treat inventory, exact availability and successful execution as unverified unless supplied. A generic methodology alone is insufficient.
- **Calibration.** Use explicitly non-target/development models for choices that can change the pool. If a suggested family may overlap the final population, distinguish a plumbing or smoke run from independent calibration, or make eligibility conditional on separation. Several sizes from one family do not by themselves establish independence.
- **Final population and timing.** Reserve the leading models on the owner's intended index (or an unambiguous equivalent description of that population) for final evaluation after fixing the benchmark, without using those outcomes to tune the pool. A generic bigger-model test or a frozen test split alone does not identify that population. Score population and freeze timing separately as well as jointly. Keep partial, unclear, contradicted and missing.
- **Joint pass.** A usable plan meets calibration, final population, and freeze timing in the same delivery. Record current and full history separately. Claim a repeatable history signal on this case only if both full-history plans pass and current-only passes fewer. If it fails, still report all cards and comparisons but qualify any history-benefit interpretation. For each fixed card require both revised deliveries to pass; show old-reader passes and any lost component on that same card. Claim a replicated reader advantage only if the history signal holds, both revised pairs pass, neither card loses a joint pass versus its own old reader, and at least one improves. Equality remains a valid result. These are within-task diagnostics, not population estimates.
- **Other tradeoffs.** Track order versus using ranking agreement to tune, related-model independence, hardware priority, and local availability/storage constraints. Distinguish earlier preferences, assistant-proposed details and limitations the current exchange already gives away. Flag unsupported access, current rankings, machine state or new owner commitments. Absence of an unrelated detail from a plan alone does not imply compression loss.

Lock the local analyst's judgments before revealing assignments or inspecting either card. Afterwards trace each target and collateral detail through the prior text, detailed extraction, card and both deliveries. Distinguish a missing qualification in extraction from one the reader did not apply. Record whole-card lengths, usage, per-read results and missingness. One owner, one previously unevaluated task, two generated cards; no independent human acceptance or live GPU experiment.
